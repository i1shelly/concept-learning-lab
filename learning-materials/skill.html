Skill（技能）

把"这件事经常这么做"的经验固化成文件夹，让 AI 按需翻阅的可复用操作手册

学习主题：Skill ｜ 生成日期：2026-09-08 ｜ 初稿由 AI 按 Skill 流程生成，经作者核查（记录见仓库 README）

1学习目标

  1. 能解释 Skill 解决什么问题、由哪些部分组成
  2. 能描述渐进式披露（progressive disclosure）的三层加载机制，并说明它为什么省上下文
  3. 能区分项目级与用户级 Skill，并判断一个任务是否值得沉淀为 Skill

2核心问题

  • 为什么不把所有用法说明直接写进系统提示词？
  • Skill 和"保存一段提示词模板"有什么本质区别？
  • 本次作业为什么要求做成 Skill，而不是写一段一次性提示词？

3我的解释

Skill 是把"这件事我经常让你做、而且每次做法都一样"的经验从对话里搬出来，固化成一个文件夹：一份 SKILL.md 写清楚何时触发、按什么步骤做，旁边还可以放脚本和参考资料。

最妙的设计是"渐进式披露"——AI 平时只记每个 Skill 的一行简介（几乎不占上下文），真正遇到匹配的任务才翻开整本说明书，引用到的附件才按需去读。它像给 AI 配了一本"可扩展操作手册"。我这次亲手写的 concept-learning 就是例子：把我"先查证来源、再结构化输出、最后自测"的学习流程沉淀成工具，以后学任何新概念，一句话就能启动同一套严谨流程。

4核心机制与组成

Skill 的解剖

一个 Skill 本质上是一个目录，核心是 SKILL.md（YAML 元数据 + Markdown 指令正文），可选地带脚本、参考文档和模板资源：

my-skill/
├── SKILL.md        ← 必须：元数据（name、description）+ 指令正文
├── scripts/        ← 可选：可执行脚本
├── references/     ← 可选：参考文档
└── assets/         ← 可选：模板、资源

渐进式披露：三层加载

层级加载时机内容Token 开销
第 1 层 · 元数据启动时，常驻系统提示每个 Skill 的 name + description约 100 token/个
第 2 层 · 指令任务匹配、Skill 被触发时SKILL.md 正文建议 < 5K token
第 3 层 · 资源正文引用到才读取参考文档、脚本（脚本只回传输出，代码本身不进上下文）访问前为零

这正是它能与上下文协作的关键：装几百个 Skill，Agent 平时只"知道它们存在"（第 1 层的元数据总开销很小），用到哪个才展开哪个——上下文这张"桌子"不会被闲置的手册占满（对照阅读：本仓库 llm-context.html）。

两级存放

层级目录适用
项目级{仓库}/.workbuddy/skills/随 git 仓库走，团队/课程共享——本 Skill 所在位置
用户级~/.workbuddy/skills/个人全局，所有项目可用

开放标准

Skill 的格式源自 Anthropic 的 Agent Skills（2025 年 10 月推出），同年 12 月发布为开放标准，已获 Claude Code、Cursor、VS Code Copilot、Codex CLI 等十余种工具支持；WorkBuddy 的技能体系与该规范同源兼容——本仓库的 Skill 在两类工具里都能用。

5应用场景：本仓库就是自证

没有 concept-learning 之前，每学一个新概念都要重新交代一遍要求："要有学习目标、要有核心问题、来源必须真实、要附自测题……"。有了它，一句"用 concept-learning 学习 X"就启动整套流程——本仓库的三份资料就是这么产出的：Skill 是模具，资料是翻模件。

而且因为它放在项目级目录、随 git 仓库走：任何人克隆这个仓库、在 WorkBuddy 里打开它，都能用同一个模具继续生产新的学习资料。这就是"沉淀可复用的任务知识"的含义——流程知识不再散落在某次对话里，而是变成了仓库里可版本管理的资产。

6概念辨析与边界

容易混淆的对象区别在哪
提示词模板模板是"一段文字"；Skill 是"说明书 + 脚本 + 参考资料"的目录组织体：能执行代码、能按需加载、能进 git 版本管理
MCP / 插件MCP 解决"连得上"（外部系统的接入协议）；Skill 解决"做得好"（任务知识的封装）。一个递工具，一个教方法
微调 / 训练Skill 不改模型权重，只是运行时"递到手边的操作手册"，随时可改、可撤、可分享

使用边界

  • 适合高频、重复、流程可固化的任务模式；一次性任务直接对话更划算
  • 判断口诀：当你第二次对 AI 说同样的要求时，就该考虑写成 Skill 了
  • SKILL.md 的 description 要写清触发场景——写得太泛会导致误触发，写得太窄又会漏触发

7自测

1.（简答）渐进式披露分哪三层？为什么这个设计能省上下文？

参考答案

元数据（启动常驻）→ 指令正文（触发才载入）→ 参考资源（引用才读取，脚本只回传输出）。未触发的 Skill 只占约 100 token，大块内容只在需要时进入上下文，因此装很多 Skill 也不会挤爆窗口。

2.（选择）想让技能随仓库共享给他人使用，应放在？　A. 用户级 ~/.workbuddy/skills/　B. 项目级 .workbuddy/skills/　C. 任意文件夹　D. 桌面

参考答案

B。项目级技能随 git 仓库分发，克隆即可获得。

3.（判断）Skill 和 MCP 是一回事，都是给 AI 接外部工具。

参考答案

错。MCP 是连接外部系统的协议（解决"连得上"）；Skill 是封装任务知识的方法论（解决"做得好"）。

4.（简答）什么样的任务值得沉淀成 Skill？

参考答案

要点：高频重复出现、做法能固化成明确步骤、希望跨会话/跨人复用——例如本作业的资料生成流程。
